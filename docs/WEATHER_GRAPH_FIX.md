# Диагностика пустых погодных графиков

12 ноября 2026. Проверены прямые реальные Open-Meteo запросы, преобразование ответа, FastAPI/Next.js API и отображение в Chromium. Синтетические погодные значения в приложение не добавлялись.

Дополнение: последующая диагностика установила причину отсутствия волн южной точки — выбор `nearest`. Переключение Marine на `sea` восстановило реальный прогноз. См. [MARINE_CELL_FIX.md](MARINE_CELL_FIX.md); приведённый ниже результат с null относится к прежнему запросу.

## Что установлено

Прямой Weather API и Marine API вернули HTTP 200 для пакетов всех настроенных точек. Для «Северного Каспия» (44.1, 48.4) получены 72 числовых `wind_speed_10m` в m/s и 72 `wave_height` в m. Ячейки модели близки к запрошенной точке: Weather примерно 44.12547, 48.39222; Marine 44.125, 48.375015. Для этой проверки отсутствие координатного покрытия Северного Каспия исключено.

Ответы используют `hourly.time` в Unix-секундах UTC, как запрошено `timeformat=unixtime`. API CaspiFlow формирует timezone-aware ISO UTC, frontend переводит их в МСК. Единицы и временные метки здорового реального ответа корректны. Поля, статусы, выбранные ячейки, диапазоны и первые реальные значения сохранены в [weather_http_diagnostics.json](weather_http_diagnostics.json).

Для южной точки 39.7, 49.2 Marine вернул HTTP 200 с `wave_height: null` во всех часах. Это реальное отсутствие числового покрытия конкретной ячейки/периода, а не нулевые волны. Ветер этой точки доступен. На сухопутной точке волны вообще не запрашиваются.

## Причина и границы вывода

В коде обнаружен и воспроизведён дефект пакетного разбора: исключение из-за одной точки (неправильная единица, отсутствующий объект или массив, несовпадение длины) выходило из `fetch_provider`. WeatherService затем заменял весь результат этого источника пустым словарём — включая исправные точки. Аналогичный результат давал тайм-аут/HTTP-отказ всего источника. Графики получали null и выводили общий текст, не объясняющий конкретную причину выбранного ряда. Кнопка «Обновить прогноз» не обходила кэш отказа, поэтому немедленный повтор не выполнялся.

Нельзя достоверно восстановить точную сетевую ошибку или повреждённое поле **первоначального пользовательского запроса**: его upstream-ответ и подробный журнал не сохранялись. На момент прямой проверки оба источника уже отвечали нормально. Поэтому отчёт не приписывает прежний сбой недоступности координат или подтверждённому HTTP-статусу, которого нет в исторических данных. Исправлен воспроизводимый механизм потери пакета и недостаточная диагностика; новый ответ позволяет отличить отказ HTTP, тайм-аут, некорректную точку, временной диапазон и отсутствие покрытия.

## Исправления

- Независимый разбор каждой точки, сопоставление по location_id или координатам. Ошибка одной точки не уничтожает остальные.
- Укороченные массивы и отдельные неправильные часы оставляют корректные значения; пропуски остаются null.
- Поддержаны Unix-секунды и ISO UTC. Миллисекунды и неверные часовые метки не притворяются правильными. Окно фиксируется до сетевого I/O, чтобы ответ через границу часа не смещал прогноз.
- Для каждой точки и источника возвращаются HTTP-статус, поле/единица, ячейка, диапазон ответа, число часов и причина. Полный отказ содержит понятное описание, включая HTTP 429 и тайм-аут.
- Ветер отображается независимо от волн. Полный индекс остаётся отсутствующим при неизвестном обязательном факторе; известные ветровой/волновой показатели показываются отдельно как частичные, без названия «вероятность».
- Статус «Недостаточно данных», конкретные причины и кнопки повтора видны рядом с графиками.
- «Обновить прогноз» и «Повторить запрос» вызывают `/forecast?retry=true` и обходят ещё не истёкший кэш. Повтор ограничен одним внешним обновлением за 10 секунд; при ограничении UI показывает оставшееся время, не выдавая прежний ответ за новый.

Никакой интерполяции выдуманными волнами, заполнения нулём или переноса соседней морской ячейки без маркировки не выполняется. Методика ML, ручная симуляция, админ-сессии и таможенные функции сохранены.

## Проверка

Backend регрессии проверяют повреждённую точку, null-объекты, укороченные и переставленные пакеты, ISO-время, частичные часы, HTTP 429, тайм-аут Marine с доступным ветром, смену часа, несовпадение горизонта и восстановление повтором запроса. Исходные backend-тесты также проходят.

Playwright проверяет все семь точек по реальному `/api/forecast`, сверяя наличие каждого графика с числовыми часами API. Дополнительно проверены отказ волн с доступным ветром, частичный показатель, линия с разрывами и запрос `retry=true` с восстановлением. Частичные отказы в этих тестах — тестовые fixtures, не fallback приложения. Ручная симуляция, ML, карта, экономика, таможня и admin входят в общий регрессионный набор.

Живой повтор запроса также выполнен без mocks: HTTP 200, fetched_at изменился, для Северного Каспия снова получены 72 часа ветра и волн. Доказательство — [weather_retry_probe.json](weather_retry_probe.json).

Фактические результаты и метаданные по каждой точке сохраняются в [weather_chart_probe.json](weather_chart_probe.json). Скриншоты сделаны с реального ответа, не с fixtures:
